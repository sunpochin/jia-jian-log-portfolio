# 飲食與體重 / Nutrition and weight

每餐、食物快取與體重都是被照護者的照護事實，必須以 `patient_id` 作唯一歸屬；`recorded_by` 只記錄實際輸入者，不能取代病人 UUID。這讓兩位照護者可替同一人持續補登，也避免代填者自己的帳號 email 把資料拆散。

`meal_records` 保存餐次與實際發生時間，`meal_record_items` 保存當時的品名、份量與 kcal 快照。快取 catalog 後來被修正時，不得回寫歷史餐點。`meal_food_catalog_items` 只限同一病人的授權照護者模糊搜尋；使用者手輸或未確認的 AI 結果不可自動變成其他家庭的公開資料。

每日照護把「飲食」與「體重」作為兩個可獨立顯示的區段，讓只需要體重的使用者不必先打開飲食；兩者仍共用同一個 `patient_id`，不新增額外底部導覽。每日總熱量只加總已確認的數字，未知值要明示未完整，不得悄悄視為零或醫療建議。

飲食模組另含「近期趨勢」，以每日熱量合計呈現。沒有任何紀錄的日子留白而不是 0，因為「那天沒記錄」與「那天吃了 0 大卡」在照護判讀上完全不同；已填與未填熱量混合時只加總已填的數字。彙整規則在 `src/lib/trendSeries.ts`，回歸測試在 `tests/unit/trendSeries.test.ts`。

飲食的「今天」使用台北日曆日（`startOf('day')`～`endOf('day')`），與服藥的照護日（04:00 換日）刻意不同：一餐屬於哪一天由用餐當下的日曆日決定，不隨照護排班移動。日界線必須隨時間重算而不是只在掛載時算一次 —— 這個 App 以 PWA 常駐在手機上，不會每天重新掛載，固定的日界線會讓「今日合計」與「今天的餐點」跨過午夜後一直停在前一天。目前以每分鐘更新的台北日期字串作為重算依據。

拍照辨識屬後續選用功能。它只能在伺服器端以 secret 呼叫，回傳的品名／kcal 必須由照護者確認才可儲存；預設不長期保存原始照片，避免把影像與健康資料不必要地擴散。
