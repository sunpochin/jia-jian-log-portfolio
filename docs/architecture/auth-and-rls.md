# 身分驗證與 RLS / Auth and RLS

## 安全邊界

Google Identity Services 只證明登入者身分；前端 route guard 只改善體驗。Supabase anon key 會出現在瀏覽器，因此所有 SELECT、INSERT、UPDATE、DELETE 與 RPC 權限都必須由 RLS／資料庫函式強制執行。任何「前端看不到」的資料都仍要能抵抗直接 REST API 呼叫。

## 登入流程

1. 使用者在公開登入頁閱讀條款與隱私連結，點擊 Google 官方按鈕。
2. Google 在 popup／FedCM 完成帳號選擇，把 ID token credential 回傳給前端；前端以原始 nonce 呼叫 `supabase.auth.signInWithIdToken()`，不把使用者導到 Supabase project-ref 網域。
3. nonce 每次登入重新產生；Google 收到 SHA-256 hex，Supabase 收到原始值，讓 Auth 能驗證 token 沒有被重放。
4. session 取得後，資料庫以 Auth UID／JWT email 對應 profile。
5. 未授權帳號看到雙語拒絕頁，不建立可讀寫家庭資料的捷徑。
6. 新家庭使用 transaction RPC 一次建立 profile、household、owner membership 與第一位 patient，避免前端分五次寫入留下半套帳戶。

LINE 內建瀏覽器不適合完成 Google GIS 登入。App 不再用 `location.href` 在 LINE 內自我重新整理，因為那只會留下同一個 WebView；偵測到 LINE 時改顯示雙語提示與 `target="_blank"` 外部瀏覽器連結，讓使用者明確在 Safari／Chrome 完成登入。這也避免第一筆照護資料寫入後，第二次操作因 WebView session／Google popup 限制而看似「跳出 App」。

GIS 按鈕仍需要 Supabase Dashboard 的 Google provider 啟用並設定同一個 Google Web Client ID／secret；差異只在前台不再使用 Supabase OAuth callback redirect。`VITE_GOOGLE_CLIENT_ID` 是可公開的瀏覽器設定，不是 secret；允許登入的帳號仍由 `profiles` 與 RLS 決定。

### Capacitor 原生登入轉接（Issue #544）

Capacitor iOS 只把既有 Vite `dist/` 放進原生殼；`src/lib/nativeAuth.ts` 是薄 adapter，使用 `signInWithOAuth({ skipBrowserRedirect: true })` 取得 Supabase authorize URL，再交給系統瀏覽器，回到固定的 `jia-jian-log://auth/callback` 後只接受 PKCE `code` 並呼叫 `exchangeCodeForSession()`。Web／PWA 不走這條路，仍使用上面的 GIS ID-token 流程；因此不會為 iOS 複製一套 React UI、資料模型或 session store。

callback parser 只接受固定 scheme／host／path、PKCE 相關欄位與有限長度，拒絕 fragment、authority credentials、token query 參數與未知欄位；OAuth error 只回傳固定哨兵值，不把 provider 描述帶進畫面或 log。交換前釋放 adapter 持有的 code，callback 由原生 event 直接交給 Supabase，不寫入 adapter 自己的 localStorage、analytics 或錯誤訊息。PKCE verifier 與 session persistence 仍由共用 Supabase client 管理，這是「冷啟動可恢復」與「不自行複製 token 管理」之間的必要邊界。

原生殼不改變授權：健康資料查詢仍須由登入後 session、明確的 `care_access.patient_id` 與既有 RLS 放行；未授權帳號不能因知道 deep link 或 patient UUID 而讀取資料。本 issue 不新增 migration、不放寬 RLS、不加入通知、HealthKit 或 SwiftUI 第二套畫面；Simulator／staging OAuth redirect allowlist 與正反授權資料矩陣仍是人工驗收 gate。

email 比對要用防禦性的不區分大小寫方式；但 email 不能成為 patient 的資料主鍵。

## 授權模型

`care_access.patient_id` 或 `household_members` 是可讀寫範圍的明確來源。每筆資料的 policy 必須同時檢查登入 UID、目標 patient 與操作類型；代填者的權限不應被誤當成病人本人。

`care_access` 對 `authenticated` 只開放 SELECT，且 policy 只認 `user_id = auth.uid()`；`20260822100000_grant_authenticated_care_access_select.sql` 是補足 PostgreSQL table privilege，不是把授權表變成可任意瀏覽或可直接修改。新增／修改／撤銷 access 仍必須走受控 RPC，健康資料的 RLS 也會再次以 `patient_id` 驗證。

`care_access` 的授權身分已經從「誰控制這個 email」改綁「哪一個 `auth.users.id`」（F-5，issue #590，三個施工單位均已落地）。單位 1（`20260913160242_bind_care_access_to_auth_user_id.sql`）加上 `user_id UUID REFERENCES auth.users(id) ON DELETE CASCADE`；單位 2（`20260913165000_bind_care_access_rpcs_to_auth_user_id.sql`）把繞過 RLS 的 `SECURITY DEFINER` RPC 與 service-role Function 也改走身分綁定；單位 3（`20260914130000_drop_care_access_email_fallback.sql`）拿掉了 email 過渡軌：`user_id` 改 `NOT NULL`、policy 與 `current_care_access` helper 只認 `user_id = auth.uid()`、`bind_care_access_user_id` trigger 解析不到「恰好一筆」`auth.users` 匹配就 `RAISE EXCEPTION`（fail closed，不再留下過渡列），並在正規化殘留重複列後把 `(user_id, patient_id)` 從非唯一索引升級成唯一約束。因為 94 條下游 policy 都是透過查詢 `care_access` 取得授權，這個單一關卡改完後全部自動只看得到 `auth.uid()` 名下的列，不需要逐條重寫。**email 不再是照護者身分的判斷依據**，只保留在 `profile_email` 欄位當稽核快照與既有外鍵。上線前置條件（staging／production 各查一次 `user_id IS NULL` 計數並處置非零列）仍待人工執行，migration 本身已把它做成 runtime 自我防護。詳見 [`care-access-identity-binding.md`](care-access-identity-binding.md)。

單位 3 之後曾有一段過渡期，整體授權是「`care_access` RLS 先以 `user_id = auth.uid()` 篩列」AND「下游 policy 仍比對 `LOWER(access.profile_email) = LOWER(auth.jwt() ->> 'email')`」（issue #774）。安全面只收緊、不放寬——偽造 email claim 拿不到任何健康資料；可用性面則有一個缺口：Google 帳號改了 email，JWT email 變了但 `profile_email` 快照沒同步，該使用者會失去所有既有病人的讀寫。#774 分兩步關掉這個缺口。做法 2 先止血：`20260914150000_sync_care_access_profile_email_on_login.sql` 是一支只做快照對齊的 `SECURITY DEFINER` RPC `sync_care_access_profile_email()`：把「本人 `user_id` 名下」的列的 `profile_email` 同步成本人剛驗證過的 JWT email——只改自己的列、只改這一欄、不動能力欄位與 `patient_id`，所以不會新增或放寬任何一筆授權；新 email 還沒有 `profiles` 列（首次登入尚未 provision）時是 no-op；同一位 patient 若已有一列「新 email 但綁在別的 `user_id`」的殘留授權，就略過本人那一筆而不是撞 `(profile_email, patient_id)` 唯一鍵讓登入失敗；同步本身失敗也只回 0 並寫 WARNING，不阻斷呼叫端。前端 `profileForEmail()`（`src/lib/auth.ts`）每次解析身分都先呼叫它、再讀 `profiles`／`care_access`；`auto_provision_profile()` 首次 provision 時也呼叫一次。為什麼不能只放在 `auto_provision_profile()`：前端只在「這個 email 還沒有 `profiles` 列」時才呼叫它，被邀請過的 email、有待接受邀請而延後 provision 的帳號、或曾因唯一鍵守門略過同步而 owner 之後才撤銷殘留授權的帳號，之後的登入都不會再經過它。`supabase/tests/rls-authorization.sql` 的 `f5_unit4_email_sync`／`f5_unit4_email_sync_conflict` 兩組 savepoint 覆蓋 no-op 前提、首次 provision 同步、冪等、不碰旁觀者的列、唯一鍵守門與撤銷後由獨立 RPC 補同步。做法 1 接著拔掉病根：`20260915100000_bind_downstream_policies_to_care_access_user_id.sql` 用 `ALTER POLICY` 逐條把 101 條下游 policy（40 張表，含 `storage.objects` 的 5 條；清單是靜態重播全部 migration 的 `CREATE`／`ALTER`／`DROP POLICY` 取每條最後定義建構出來的，文件先前寫的 83／94 都只是盤點快照）的 `care_access` 子查詢述詞從 email 比對換成 `access.user_id = auth.uid()`。policy 名稱、指令、角色與其他條件——`patient_id` 對應、`can_record`／`can_manage_medication` 能力位、`recorded_by`／`created_by`／`account_email` 等記錄者稽核、`is_admin_email()`、storage bucket／path 前綴——逐字不動；`care_access` 自身 RLS 本來就只回本人 uid 的列，所以這一步只是把多餘的 AND 拿掉，不會讓任何人多看到任何一位病人。migration 檔尾以 `pg_depend` 自我檢查（查 policy 對 `care_access.profile_email` 欄位的 catalog 依賴，不比對 `pg_policies` 反解析文字，別名或引號怎麼寫都躲不掉）沒有任何 policy 還在比對 `access.profile_email`，漏一條就讓 `db push` 失敗；`ALTER POLICY` 對不存在的 policy 也直接報錯，不用 `IF EXISTS` 靜默略過。現在整條授權鏈只認 `auth.uid()`，`profile_email` 快照對不對已不影響任何一張健康資料表的讀寫；同步 RPC 保留作稽核快照對齊（無害）。`rls-authorization.sql` 的 `f5_unit3_uid_only` (c) 與 `f5_unit4_email_sync` 的前置斷言因此反轉成「快照過期仍讀得到」，「正確 email、錯誤 sub 讀不到」的既有斷言不變——uid 仍是唯一關卡。`active_patient_preferences` 三條 policy 裡比對「這一列是誰的」的自身 `profile_email` 欄位不是 `care_access` 快照，不在此範圍，維持原樣；`drug_products`／`medications` 等目錄表以 `profiles.email` 成員資格放行的 policy 也未動。

媽媽帳號 `demo.mother@example.test` 的 `profiles.patient_id` 是唯一可操作對象。家庭成員／寵物同步不得把 household membership 轉成她對其他 patient 的 access；`20260815010000_enforce_mother_patient_only_access.sql` 會清理既有 foreign grants 與 stale active-patient preference，並在 `care_access` 寫入前阻止再次授權。這個資料庫閘門與前端 `profileForEmail` 的 own-patient 過濾互相獨立，避免只靠畫面隱藏造成服藥或其他健康資料旁路。

被照顧者加入採兩階段授權：`create_household_patient_invitation` 只由 owner 建立人類 patient 與待接受邀請，不寫入 `care_access`；受邀 Google 帳號只能透過 email 綁定的 `accept_patient_care_invitation` 接受，成功後才建立被照顧者自己的 access 與邀請照顧者的 access。待接受邀請查詢也回傳由 `auth.users`／`app_profiles` 衍生的邀請人姓名與 Email，供被照顧者在同意前核對，不把可自由填寫的授權依據當成身分證明；查詢錯誤不得被當成空結果而觸發 auto-provision。邀請 table 不開放直接 SELECT／寫入，避免 client 以任意 patient UUID 或 email 偽造授權。

生理數值與會改變健康判讀的病人專屬目標／警示門檻，不論從輸入表單、圖表、匯出、通知或快取進出，都必須先解析並驗證目標 `patient_id`。「自己」只是 UI 關係描述，不是授權捷徑；資料庫仍要把登入者對應到可存取的 patient。純顯示偏好可以只檢查 `auth.uid()`，但一旦設定會影響特定病人的健康判讀，就必須改走 patient 授權。

內分泌模組遵守同一個邊界：`pet_blood_glucose_target_ranges.patient_id` 是血糖 target 的唯一分區鍵，讀取 policy 只允許該 JWT 對應的 `care_access.patient_id`，更新只能由 RPC 再驗證 `can_record`。`record_pet_endocrine` 不信任前端的 actor email 或 active tab，先驗證明確 patient access，再在同一交易內寫入胰島素與血糖；invalid value 或撤銷 access 會讓整次寫入失敗。這避免「頁面隱藏了病人」或「第一個 request 成功」被誤當成授權／一致性的證據。

核心照護不變量：`admin@careapp.local` 與 `demo.caregiver@example.test` 必須持續能讀取、寫入照護紀錄並管理 `demo.mother@example.test` 對應病人的藥單。任何 RLS 或家庭管理變更都要以 staging 測試這條 read/write 路徑。

既有帳號若在家庭搬遷 migration 之後才首次登入，可能已有明確的 `care_access` 卻尚未有 `household_members`。`20260811010000_repair_core_household_memberships.sql` 只對三個已確認核心帳號，沿著完整 `care_access` 的 `patient_id → patients.household_id` 補回對應 membership；找不到完整授權時不建立任何 membership，也不覆蓋既有角色。這讓家庭管理 RPC 能工作，同時不把任意登入帳號的病人存取權推論成家庭成員資格。

因為前一版 `20260811010000` 可能已先部署到 staging，`20260811020000_repair_viewer_household_membership.sql` 以同樣的冪等策略補 viewer 的最小明確存取條件，確保已部署環境也能完成修復。

`user_settings` 是例外的帳號層偏好，不需要 `care_access`：每個 policy 都以 `user_id = auth.uid()` 限制本人讀寫，client 傳入的 UID 仍不能越過 RLS。它只保存介面閱讀習慣，不含 patient 或健康事實，因此不會改變核心照護授權不變量。

`patient_daily_care_preferences` 是被照護者共用的顯示偏好，policy 只允許透過 `care_access.patient_id` 授權的照護者讀寫該病人的共同設定；它不能讓未授權帳號藉由偏好列取得血壓、服藥或其他健康資料，資料本身仍由各 feature table 的 RLS 保護。舊的 `user_patient_care_preferences` 保留作 migration 相容與稽核參考，不再是現行讀寫來源。

共用顯示偏好的 INSERT／UPDATE／DELETE 以及舊表的 INSERT／UPDATE 都要求 `care_access.can_record`；view-only 照護者仍可讀取，但不能藉由舊版 PWA 間接改動共同入口。過渡期內，舊表的新增／更新由 invoker trigger 同步到共用表，共用表變更則由受控的 `SECURITY DEFINER` trigger 回填所有舊列；雙向 trigger 以 trigger depth 防止遞迴，避免舊版分頁成功寫入卻讓新客戶端看到另一套設定。

照護大事記照片使用 private `care-event-photos` bucket，不使用 public URL。Storage object path 的病人 UUID 只作分區索引，真正的 SELECT／INSERT／DELETE policy 仍查 `care_access`；資料表 CHECK validator 還會逐筆比對 `patients/{patient_id}/events/{id}/` 前綴及原圖／縮圖成對命名，避免有權限看多位病人的照護者藉由手寫 JSONB path 交叉引用照片。前端只在時間線列表簽署縮圖，單張（尤其剛上傳的第一張）直接使用單檔 endpoint，點擊時才簽署原圖；批次簽署缺項時改用單檔 endpoint 補簽，URL 過期時重新簽署，並在原圖失敗時保留預覽退路，這些行為都不改變 private bucket、caller session 或 RLS，signed URL 也不回寫資料庫。藥品目錄的 TFDA 外觀圖則透過本站 Vercel Function 代理，proxy 只接受精確官方圖片路徑，不把第三方 host 加入瀏覽器 CSP，也不允許任意外部圖片來源；它不隱藏公開圖片或 path，只把直接聯絡者從照護者裝置換成本站伺服器，降低第三方把裝置與藥品瀏覽行為連結的能力。保留層級放在無 client grant 的 `account_usage_limits.photo_retention_tier`；service-role 清理 Function 只刪 private Storage API 允許的 path，完成後才清空事件 metadata。

PRN 使用事件與每日 assessment 都以 `care_access.patient_id` 為讀寫邊界，寫入要求 `can_record`；事件另外要求 JWT 的 `auth.uid()`／email 與記錄人一致，並確認 plan、medication、patient 三者相符且 plan 是 `as_needed`。事件只能由 active 轉為 voided，資料庫 trigger 鎖住實際時間、病人、藥單、記錄人等稽核欄位。這條路徑不依賴 household membership 或前端隱藏按鈕，因此不會削弱 portfolio-author 與 caregiver 對媽媽 patient 的既有明確授權。

調藥 RPC 仍以 `care_access.patient_id` 與 `can_manage_medication` 驗證，`auth.uid()`／JWT email 只作 actor 稽核欄位；時間線 system event 的 linkage 由 SECURITY DEFINER RPC 建立，authenticated INSERT policy 明確拒絕 `medication_change` 與非 NULL linkage。UPDATE／DELETE policy 與資料庫 trigger 同時拒絕修改或刪除 linked system event。staging 驗證時必須用 `admin@careapp.local` 與 `demo.caregiver@example.test` 對 `demo.mother@example.test` 的 patient 實測讀取、建立／調整／停用 plan，並確認兩張表各只有一筆對應事件。

服用方式 B 層 `patient_medication_instructions` 的 RLS 照抄同一份 `care_access` 條件，不另立新規則：SELECT 只要求該 `patient_id` 的 `care_access`；INSERT／UPDATE／DELETE 再加 `can_manage_medication`（跟 `medication-appearance-photos` bucket 的寫入條件同一把鎖）。`updated_by` 由 trigger 以 `auth.jwt() ->> 'email'` 強制寫入，不接受前端傳值，因此稽核來源不能被偽造。這張表不經過 `apply_medication_plan_change`——它只描述「這位病人的這顆藥」怎麼吃，不動處方本身，因此一般 `supabase.from()` 讀寫即可，不需要 RPC，也不寫入 `medication_plan_change_logs`。

Calendar 通知的 `calendar_notification_sources` 與 `notification_deliveries` 也只允許 authenticated 使用者以 `care_access.patient_id` SELECT 自己被授權病人的狀態。兩張表沒有 authenticated 的 INSERT／UPDATE／DELETE policy，且 SQL privilege 明確 revoke client DML；這使瀏覽器不能手動建立 delivery、跳過唯一去重鍵或把 source 接到另一個病人。Supabase Cron 呼叫的 Edge Function 使用 server-only service role，但 Function 的 HTTP 入口仍以 `CALENDAR_NOTIFIER_CRON_SECRET` 驗證，因為它不是照護者 JWT。這條路徑用 service account 讀取已分享的專用次要 Calendar，不修改現有 Google GIS scope，也不把 Google OAuth token 交給前端。

`care_due_reminders` 延續同一個病人級邊界：一般照護者只能 SELECT 自己有 `care_access` 的提醒，新增／修改／刪除必須同時有該 patient 的 `can_manage_medication`；delivery audit 只允許授權讀取，寫入與狀態轉移只由 Cron service role 執行。提醒表與 delivery 以 `(reminder_id, patient_id)` 複合外鍵再驗一次歸屬，避免只換 UUID 就把送達紀錄接到另一位病人；`supabase/tests/rls-authorization.sql` 同時覆蓋已授權建立與未授權拒絕。照護閉環 T2（issue #946，migration `20260925190000`）沿用同一招把提醒連回臨床來源：`related_entry_id`／`related_lab_result_id` 各以 `(欄位, patient_id)` 複合外鍵參照 `care_timeline_entries(id, patient_id)`／`patient_lab_results(id, patient_id)`（兩張來源表為此各補一個 `UNIQUE (id, patient_id)`），所以「病人 A 的提醒指向病人 B 的事件」在資料庫層就被 23503 擋下，不依賴 policy 或應用層記得檢查；`ON DELETE SET NULL (欄位)` 只清空關聯欄位、不動 `patient_id`。policy 主體不變，仍是讀取看 `care_access`、寫入看 `can_manage_medication`；測試另加「有 `can_record` 無 `can_manage_medication` 改不到新欄位」與跨病人引用被拒的案例。

`calendar-agenda` 不是 Cron endpoint：它保持 `verify_jwt = true`，用 `withSupabase({ auth: 'user' })` 的 caller-scoped client 驗證登入者並查詢同一張來源表的 `patient_id` 與 `agenda_enabled=true`。它不使用 service role，因此 caregiver 只會取得她已有 `care_access` 的媽媽來源；request 不接受 calendar ID、email 或任意 source ID，避免前端把自己的日曆改接到別人病人。Google 資料只在 Function 與 React 記憶體短暫存在，沒有新增可由 RLS 誤讀的 event table。

`blood-pressure-notifier` 不是資料寫入捷徑：它保持 `verify_jwt = true`，只接受 `recordId`／`patientId`，再用同一個 caller-scoped client 精確讀取血壓紀錄與病人名稱。RLS 先限制該 JWT 能看到的 `patient_id`，Function 再要求 `recorded_by` 與 JWT email 相同，避免有權讀取多位病人的照護者代送別人的 Telegram 提醒；血壓數值與名稱不信任瀏覽器 payload，也不使用 service role。這讓 `admin@careapp.local`、`demo.caregiver@example.test` 對媽媽 patient 的既有 read/write access 直接沿用資料庫授權，不需要帳號白名單。

血壓通知的 delivery ledger（`blood_pressure_notification_deliveries`）從 issue #707 起把寫入綁到記錄者本人：原本只檢查 `care_access` 的寫入 policy 會讓同一 patient 的另一位照護者直接把別人那筆血壓的 delivery 偽造成 `sent`，讓真正的 notifier 呼叫誤判已送達而壓下警示。現在 Function 的 reserve／confirm 走 `reserve_blood_pressure_notification_delivery`／`confirm_blood_pressure_notification_delivery` 兩支 `SECURITY DEFINER` RPC，RPC 內先過 `current_care_access()`，再要求該筆 `blood_pressure_records.recorded_by` 等於呼叫者 JWT email——「誰量的這筆」才是「這則警示要不要送」的唯一依據，`care_access` 只回答能不能操作這個 patient。修補分兩階段：第一階段（`20260914140000`）先建 RPC、把直接 INSERT／UPDATE policy 收緊到同一組述詞但刻意保留 grant，因為部署流程先 `db push` 再 `functions deploy`，部署視窗內的舊版 Function 才不會回 502 漏送警示；第二階段（issue #773，`20260914160000_revoke_blood_pressure_delivery_ledger_direct_writes.sql`）在確認 staging 與 production 的 Function 都已部署走 RPC 的版本後，`DROP` 那兩條 policy 並 `REVOKE INSERT, UPDATE … FROM PUBLIC, anon, authenticated`，讓 RPC 成為這張表唯一的 client 寫入入口；migration 內以 `has_table_privilege` 與 `pg_policies` 自我檢查，撤回沒生效就讓 `db push` 直接失敗。SELECT policy 與 grant 仍以 `care_access` 為界；Function 仍只拿呼叫者 JWT，沒有因此改用 service role（那會讓它讀得到收件人 chat id）。`supabase/tests/rls-authorization.sql` 覆蓋記錄者透過 RPC 的正向路徑、記錄者本人與同 patient 非記錄者直接寫表都在 privilege 這一關收到 `42501`、以及未授權帳號的拒絕路徑。

唯讀分享 Stage 2 新增兩支 `verify_jwt = false` 的公開 Function，服務沒有帳號的分享連結接收者：`share-link-exchange` 接受 raw bearer token，以 SHA-256 hash 呼叫 `redeem_patient_share_link`（只授權給 `service_role`）換成 15 分鐘的 HMAC session，兩層 hashed bucket（IP、token）rate limit 由 `check_share_link_rate_limit` 把關，任何失敗（格式錯誤、查無此連結、已撤銷、已過期、同意已撤回）一律回同一句「連結無效或已過期」，不透露差異；`share-summary` 驗證 session 簽章與到期時間後，呼叫 `get_patient_share_summary` 重新查詢連結與同意現況（不信任 session payload 本身代表授權），回傳固定的 `daily-summary-v1` 白名單 DTO（`patientAlias` 是固定的雙語物件 `{ zh: '照護對象', id: 'Objek perawatan' }`，不是單一語言字串、也不是 `patients.display_name`；加上當日台北時區血壓最新值或 `null`）。兩支 Function 與其 RPC 都不落 raw token、raw IP 或病人真實姓名於 log；response 一律帶 `Cache-Control: no-store`、`Referrer-Policy: no-referrer`、`X-Robots-Tag: noindex, nofollow, noarchive`。`SHARE_LINK_SESSION_SECRET` 由兩支 Function 共用，只存在 server-only 環境變數。 2026-09-25 起（ADR-009 T2，#936）`share-summary` 依 session payload 的 `scopeVersion` 分派：v1 走原本的 `get_patient_share_summary`，v2 走 `get_patient_share_summary_v2` 並把信封的 `patient_id`／`scope_version` 與 payload 逐字比對（不符 401），判讀在 Function 端逐筆依當時標準完成；標準讀不到或藥單資料異常回 503 而不是出貨半份。分派邏輯在可注入依賴的 `handler.ts`，五種拒絕案例與 scope 釘死由 `tests/unit/shareSummaryV2Function.test.ts` 證明。

`admin-list-users` 是唯一使用 service role 讀取 `auth.users` 的 Function，供 `/admin`「使用者管理」分頁顯示總註冊人數、各帳號 email、註冊日期與最後登入日期。它同樣保持 `verify_jwt = true`，先用 `withSupabase({ auth: 'user' })` 拿到 `ctx.userClaims.email`，比對等於 `src/lib/auth.ts` 的 `ADMIN_EMAIL`（目前僅 `admin@careapp.local`）才建立 service role client；比對失敗直接回 403，不會先建立 service role client 再篩選結果。分頁讀取 `auth.admin.listUsers()` 設有頁數上限，超過上限視為異常直接丟錯，不悄悄回傳不完整清單；回應只挑選 email、`app_profiles.display_name`、`created_at`、`last_sign_in_at` 四個欄位，Function log 只記筆數，不記 email 或姓名。這是目前唯一允許讀取全站帳號清單的路徑，前端 `AdminPage` 的 `/admin` route guard 只是體驗層，真正邊界在這支 Function 對 JWT email 的比對。它現在還一併帶出每個帳號的 `account_usage_limits.personal_notification_tier`／`medication_ai_draft_tier` 現值（依 `profile_email` 正規化為小寫比對），讓後台畫面答得出「誰是付費會員」；這兩個欄位本來就是 service role 才讀得到，沒有放寬既有 `REVOKE ALL FROM anon, authenticated` 邊界。

`admin-set-account-entitlement` 是唯一允許寫入 `account_usage_limits` 付費旗標的 Function，供 `/admin`「使用者管理」分頁的勾選框呼叫。授權判斷與 `admin-list-users` 同一套：`verify_jwt = true` → `withSupabase({ auth: 'user' })` 取得 `ctx.userClaims.email` → 比對 `ADMIN_EMAIL`，比對必須先於任何 service role 呼叫，失敗直接回 403、不建立 service role client。請求的 `entitlement`／`value`／`reason` 三個欄位都先經過白名單驗證（`supabase/functions/admin-set-account-entitlement/adminSetAccountEntitlement.ts`），即使只有 admin 打得到也不把字串直接當成 update key；`targetEmail` 一律 `trim().toLowerCase()`。Function 本身**不**分別 `update` 再 `insert` 稽核列，而是呼叫單一 `SECURITY DEFINER` RPC `set_account_entitlement`（`supabase/migrations/20260910150000_add_medication_ai_draft_entitlement.sql`），由 RPC 在同一個交易內原子完成「改 `account_usage_limits` + 寫一筆 `account_entitlement_change_logs` 稽核列」，避免兩次獨立 PostgREST 呼叫中途失敗留下「有權限沒稽核」或「有稽核沒權限」的不一致狀態。該 RPC 只授權給 `service_role`（明確 `REVOKE ALL ... FROM PUBLIC, anon, authenticated`），`account_entitlement_change_logs` 啟用 RLS 但刻意不建任何 policy，比照 `user_messaging_links`——這張表存的是誰付費、誰開的，沒有人被授權用一般連線讀取。Function log 只記事件名與 entitlement 名稱，不記 email。

管理者身分只有一個執行期來源：`ADMIN_EMAIL` Function secret（`supabase/functions/_shared/adminIdentity.ts` 是唯一讀它的地方）。Postgres RLS policy 讀不到 Deno secret，所以 `blood_pressure_records` 的 `"administrator deletes records within granted patients"` DELETE policy 改為呼叫 `public.is_admin_email(auth.jwt() ->> 'email')`（`supabase/migrations/20260914100000_read_admin_identity_from_app_admin_config.sql`，issue #738）：這是一支 `STABLE SECURITY DEFINER` 函式，只回 boolean，內部查 `public.app_admin_config` 的 `admin_email` 列。`app_admin_config` 啟用 RLS、刻意不建任何 policy，並對 `anon`／`authenticated` 明確 `REVOKE ALL`，所以任何登入帳號都無法直接 `SELECT` 出管理者是誰；但 `is_admin_email()` 對 `authenticated` 開放執行，等於一個「這個 email 是不是管理者」的確認 oracle——已登入帳號仍可能逐一猜測 email 並用回傳的 boolean 確認，只是猜不到答案本身、且要付出逐筆嘗試的成本。這是把判斷式放進 policy `USING` 子句（必須以呼叫者角色執行）的必然取捨，不是遺漏。`is_admin_email()` 則 `REVOKE ... FROM anon`、只 `GRANT EXECUTE TO authenticated`。migration 本身**不**寫入任何一列（AGENTS.md「資料治理與真人身分邊界」），那一列由 `admin-sync-identity` Edge Function 在執行期 upsert：它與另外兩支 admin Function 同一套授權（`verify_jwt = true` → 比對 `getAdminEmail()` → 403），沒有任何 request 參數，寫入值只能是 secret 讀出的 email，並記下 `updated_by_user_id`／`updated_at` 當稽核線索。它是手動觸發的營運操作，不接部署流程或排程；順序是「部署 Function → 套用 migration → 管理者呼叫一次」。在同步之前 policy 是 fail-closed（管理者批次刪除刪到 0 列），這是刻意的。更換管理者時先 `supabase secrets set ADMIN_EMAIL=...`，再由新管理者呼叫一次即可同步 RLS 側；`src/lib/auth.ts` 的前端 `ADMIN_EMAIL` 仍是獨立的體驗層常數，不在這條邊界內。CI 的 migration replay（`supabase/tests/rls-authorization.sql`）會斷言表無 API role 權限、函式權限與 `SECURITY DEFINER`、policy 定義不含字面 email，並以假 email 走一次「同步前 false → service role 寫入 → 只有該 email true」的端對端檢查。

授權表的每一次變更從 ADR-008 AUDIT-1（issue #967，migration `20260925222525_create_record_change_logs_audit.sql`）起都留痕跡：`care_access`、`household_members`、`patients` 與兩張判讀設定表掛 `log_record_change()` AFTER trigger，寫進通用的 `record_change_logs`（形狀見 [`data-model.md`](data-model.md)「其他核心表」）。讀取邊界沿用同一套 `care_access` 述詞、不引入新的授權主體：病人層列只有該病人 `can_record` 的照護者讀得到（viewer 讀不到——列的內容是另一位照護者做了什麼）；`household_members` 的列只有該家庭 owner 讀得到，判定經 `SECURITY DEFINER` 的 `is_household_owner()`（比照 `is_household_member()`：`authenticated` 對 `household_members` 沒有 SELECT grant，policy 內直接子查詢會在 privilege 這一關被擋，而放寬授權表的 grant 不是 audit 該做的事）；`patients` 的列兩者任一命中即可。表本身對 API role 沒有任何 DML、`ENABLE ROW LEVEL SECURITY` 明確寫在 migration、沒有任何外鍵、不存 email：actor 只記 `auth.uid()`，`profile_email`／`updated_by` 等 email 型欄位在 OLD 與 NEW 都先剝除再算 diff，帳號刪除後表內沒有任何可識別該帳號的字串。來源表若改了分區鍵（例如同時管理 A、B 的人把 `patient_anomaly_alert_settings` 的主鍵從 A 改成 B），audit 寫成 A 分區一筆 `delete` ＋ B 分區一筆 `insert`，A 的舊快照不會出現在 B 的照護者讀得到的列裡；issue #976 之後病人級表的 `forbid_patient_id_change` 會先拒絕這種 UPDATE（見下一段），這條分支只剩第二道防線的角色。actor 判定順序是「可信的 `app.audit_actor_kind = 'system'` 覆寫 → `auth.uid()` → service_role JWT → 其餘為 system」：`SECURITY DEFINER` 函式與 trigger 都在呼叫者 session 內跑，規則 trigger 的系統寫入（目前是 `revoke_share_readonly_for_caregiver_role` 收回 caregiver 的分享權）若不覆寫會被記成觸發它的使用者做的；覆寫只包住那段 UPDATE、結束後還原。`enforce_mother_patient_only_access` 現行本體只 `RETURN NULL` 吞掉越界寫入、不做任何寫入，所以沒有加覆寫（ADR-008 原文假設它會刪列，與部署中的本體不符；在沒有寫入可包的 trigger 裡設覆寫會漏到同一交易後面的寫入，把使用者做的事錯記成 system）。`delete_user_account` 對本人健康列的刪除以 `app.audit_bypass` 略過稽核（抹除請求要能乾淨完成），對 `care_access`／`household_members` 的移除如實記為 `user` ＋ `actor_source = 'delete_user_account'`。後續的 `20260926051643` 再修好兩類「帳號刪不掉」：發過邀請的帳號（兩張邀請表 `invited_by_user_id` 原為 `RESTRICT`，改為可 NULL＋`SET NULL`，未接受的邀請由 `delete_user_account` 先刪）與經照護者邀請加入過的帳號（`caregiver_invitations_request_pair_check` 原本讓 `requested_by_user_id` 的 SET NULL 撞 23514）；邀請 RPC 對 NULL 發出者／申請者的行為都是安全的（核准時讀不到申請者就 RAISE、待接受清單以 INNER JOIN 濾掉發出者已刪的病人邀請）。AUDIT-1 的 migration 也拿掉 `patient_bp_standards.created_by` 指向 `auth.users` 的外鍵（它沒寫 `ON DELETE`，設定過血壓標準的帳號呼叫 `delete_user_account()` 會撞 23503 整個回滾，`rls-authorization.sql` 先重現再證明修好）；標準列必須活得比設定者久，`created_by` 成為 dangling uid。這些邊界全部由 `supabase/tests/rls-authorization.sql` 的 `record_change_logs_audit` savepoint 在 migration replay 時實測：無關登入者與 viewer 零列、`can_record` 照護者只讀得到自己病人的列、家庭 owner 讀得到自家不讀得到別家、authenticated 直接 INSERT／UPDATE／DELETE 在 privilege 這一關 `42501`、superuser 也改不了列、規則 trigger 的撤銷記為 system、刪帳號成功且事後表內無 email。

病人級資料列一旦建立就不得改綁到另一位病人（issue #976，migration `20260928151436_forbid_patient_id_change_on_patient_scoped_tables.sql`）。原因是 RLS 表達不了「不得改變」：UPDATE policy 的 `USING` 只驗對舊病人有權、`WITH CHECK` 只驗對新病人有權，同時照顧兩位病人的人（例如媽媽和家裡的貓）就能把媽媽的體重紀錄或警報門檻改成貓的，違反 AGENTS.md § 3.5。通用 trigger function `public.forbid_patient_id_change()` 以 `BEFORE UPDATE … FOR EACH ROW` 掛在 29 張「`authenticated` 可 UPDATE `patient_id` 且有 UPDATE／ALL policy」的表上，`NEW.patient_id IS DISTINCT FROM OLD.patient_id` 就以 `patient_id_is_immutable` 拒絕；同值回寫（PostgREST upsert 的 `ON CONFLICT DO UPDATE` 會把 payload 的 `patient_id` 放進 SET 清單）照常通過，所以不採「收回 `patient_id` 欄位級 UPDATE grant」這條會打壞 upsert 的路。已有表專屬守門（`protect_*_audit_fields` 等）的 10 張也一併掛上，讓不變量可以精確比對。trigger 對所有角色生效（含 service_role 與 migration runner）：目前沒有任何合法的搬列路徑，將來真要合併重複病人，應該寫成明確的 migration 並在其中暫時 `DISABLE TRIGGER`。`supabase/tests/rls-authorization.sql` 在檔案最前面（測試補 grant 之前）跑 catalog 級不變量：`public` 中有 `patient_id`、`authenticated` 可 UPDATE 該欄、又有給 `authenticated`／`public` 的 UPDATE／ALL policy 的表，都必須掛一支 BEFORE、ROW 級、啟用中、沒有欄位清單與 WHEN 條件的 `forbid_patient_id_change`，否則 replay 失敗；檔尾 `patient_id_immutable_976` savepoint 再以對兩位病人都有全部能力位的照護者逐表驗證「一般欄位編輯成功、搬列被拒」（`medication_plans` 以管理者字面值身分驗證）。新增病人級表時照抄 migration 裡的那一行 `CREATE TRIGGER`。

## 健康資料同意

帳號條款同意與健康資料同意分開。健康資料同意由版本化、server-timestamp 的 SECURITY DEFINER RPC 記錄；代理人必須提供關係／授權依據，不能因 Google 登入成功就推定病人同意。公開 health-data-notice 在 GIS 登入前可讀，避免把同意流程藏在登入後。

登入 session 恢復時，`loadLegalConsentWithRetry()` 只讀取 `privacy_policy_version` 與 `health_consent_version`，不會順便改寫 `privacy_acknowledged_at`。政策版本落後時，App 先顯示 `PrivacyPolicyUpdateScreen`；使用者閱讀 `/privacy`／`/terms` 並按下確認後，才呼叫 `record_account_legal_acceptance()`。這個順序避免既有帳號在沒有重新看到新版分析揭露時，被背景載入誤記成已接受新政策。

`record_health_data_consent` 這支 RPC 寫回的版本字串，必須跟 `src/lib/legalConsent.ts` 的 `CURRENT_HEALTH_CONSENT_VERSION` 完全一致——`App.tsx` 是用字串相等比對 `health_consent_version === CURRENT_HEALTH_CONSENT_VERSION` 決定要不要顯示同意畫面，兩邊只要有一個字沒對齊，使用者按下「同意並開始使用」也會被判定成「尚未同意」，每次登入都重新看到同一個畫面。`20260904020000_allow_health_consent_type_upgrade.sql`（為了讓 legacy 帳號能明確表態 `consent_type`）用 `CREATE OR REPLACE FUNCTION` 覆寫這支 RPC 時，誤把版本字串沿用成更早的 `'2026-07-30'`，忘記跟上 `20260826140000` 已經升級到的 `'2026-08-26'`，正是這個 bug 的成因；`20260908140000_fix_health_consent_version_regression.sql` 修正版本字串的同時，也用 `UPDATE ... WHERE health_consent_version = '2026-07-30' AND health_consented_at >= '2026-09-04' AND consent_type IN ('self', 'authorized_representative')` 補回受這段迴歸期間影響的帳號：條件用「迴歸上線日期之後才產生的 health_consented_at」加上「consent_type 已經是 self／authorized_representative（不是初始值 NULL）」，鎖定「這個帳號當時確實透過同意畫面按下同意，只是被 bug 寫錯版本字串」這個唯一情境，而不是替任何尚未同意過的帳號補簽同意；並刻意排除 `20260730090000` 用 `legacy_existing_account` 類型預先核准的帳號（那兩個帳號在迴歸視窗開始前就已存在，且 `consent_type` 不在補回條件允許的兩個值內）。修正只改版本字串，不動 `health_consented_at`／`consent_type`／`authorization_basis`，讓稽核紀錄仍反映使用者實際按下同意的原始時間與身分別，之後任何新的健康同意版本升版 migration 都不該把這批已修正的列再當成例外處理。

新增或變更任何「會收到健康資料或帳號資料的第三方」時，揭露與升版要一起做：issue #424 盤點發現 Telegram（血壓通知、到期提醒、日曆提醒）、LINE（個人血壓通知）與 Resend（家庭邀請信）早已在運作卻沒有列在 `/privacy`，因此 `20260925130000`／`20260925130100` 把隱私政策與健康資料同意同日升到 `'2026-09-25'`，既有使用者下次開啟 App 會依序看到「隱私權政策更新」與「健康資料同意」畫面並重新確認。供應商文案集中在 `src/features/system-admin/notificationProviderDisclosures.ts`（`/privacy` 與 `/health-data-notice` 共用；只有真正收到健康數值的 Telegram／LINE 列為健康資料接收者，Resend 邀請信不含健康資料所以不列）。`tests/unit/notificationProviderDisclosures.test.ts` 以「檔名排序最後一支定義該 RPC 的 migration」比對兩個前端常數，不再寫死某支 migration 檔名，下一次升版或兩個平行 PR 各自升版時都能當場抓到版本不同步。改動任何通知 Function 的訊息欄位時，必須同步更新該文案檔並升版，否則就是不實揭露。

唯讀分享再增加一層 patient-scoped 能力：`care_access.can_share_readonly` 預設為 `false`，不會因既有 `can_record` 或 `can_manage_medication` 自動開啟。Stage 1 的 `patient_share_consents` 與 `patient_share_links` 直接以 `patient_id` 綁定，管理 RPC 以登入者 JWT email、目標 patient、目前 `legal_consents.health_consent_version` 與本人／代理人條件共同驗證；兩張表撤銷 authenticated 直接 table DML，避免 client 繞過稽核。這個能力只給家屬：病人所屬家庭中 `household_members.role = 'caregiver'` 的成員，其 `can_share_readonly` 由 `20260924191747` 的 trigger 在資料庫端鎖成 `false`（寫入 `true` 直接失敗；成員被改成 caregiver 時自動收回並寫稽核），不靠前端隱藏入口（issue #424 決策 E）。個別真實帳號的開關只能經 service-role-only 的 `set_patient_share_readonly` 營運 RPC，寫入 `care_access_capability_change_logs`，不寫在 migration（§ 3.3）。資料庫只接收 token hash，沒有匿名查詢入口；公開 token exchange、固定摘要 DTO、`no-store`／rate limit 與 session 失效留到後續 stage，Stage 0 合規 sign-off 前也不得套用這個 migration。

**代理同意結構化與分享告知版本（#424 D／G，2026-09-25）**：`create_patient_share_link`（結構化代理同意的定義在 `20260925120000_require_structured_share_proxy_consent.sql`；`20260925170000_add_patient_share_summary_v2.sql` 只把 scope 值域放寬到 v1／v2，其餘逐字相同）對 `authorized_representative` 只接受固定格式的 `authorization_basis`——`relationship=<spouse|child|other_family>;reason=patient_cannot_consent;guardian_status=not_court_appointed`，整串 anchored regex 比對，自由文字（含舊版 PWA 送來的）一律 `RAISE EXCEPTION`；同一版也要求分享者的 `health_consent_version >= '2026-09-25.2'`（首個揭露分享連結的健康資料告知版本；ISO 日期字串、同日修訂加 `.N`，可直接比大小），停在舊 bundle、沒被要求重新同意的使用者無法再建立任何分享連結（含 self）；另外也拒絕早於 `2026-09-25-share-v1` 的 `consent_text_version`（例如 `2026-09-04-draft`），因為新帳號在舊 bundle 上按同意時 RPC 一樣會寫入新的健康同意版本，只看帳號版本擋不住以舊草稿文字建立連結。格式由 `src/lib/shareLinks.ts` 的 `buildProxyAuthorizationBasis` 產生，`tests/unit/structuredShareProxyConsentMigration.test.ts` 直接拿 migration 裡的 regex 跑前端輸出，兩端不會漂移。沿用既有欄位而不新增欄位，是為了維持 RPC 7 參數簽章與既有 CHECK（1–200 字）；`2026-09-04-draft` 時期的自由文字列保留為稽核歷史，不加追溯性的資料表 CHECK。分享同意文字依 `scope_version` 各有一份（`src/features/care-family/shareConsentNotice.ts`）；管理頁讓家屬選 scope（預設 `daily-summary-v2`，ADR-009 T4），選單下方的告知、確認框與送給 RPC 的 `p_scope_version`／`p_consent_text_version` 都讀同一個所選 scope；文字版本依 scope 查 `SHARE_CONSENT_TEXT_VERSION_BY_SCOPE`（兩者目前都是 `'2026-09-25-share-v1'`，由 `(scope_version, consent_text_version)` 兩欄合起來指向使用者看過的那段文字），`consent_text_version` 只有長度 CHECK，所以換版本字串不需要 migration。分享連結的隱私政策與健康資料告知另外升為 `2026-09-25.2`（`20260925150000`、`20260925150100`），不沿用同日 Telegram／LINE／Resend 揭露的 `2026-09-25`（PR #919）：那個版本已在 staging 上線且不含分享段落，同一個版本字串若代表兩份不同告知，已接受舊內容的人不會被要求重新確認，版本號也就無法證明使用者看過哪一份（PR #922 Codex P1）。代價是 staging 使用者會再被要求確認一次；production 若兩者在同一次 promotion 上線，使用者會依序看到隱私政策與健康資料畫面各一次（兩者都直接跳到 `2026-09-25.2`）。

**分享摘要 `daily-summary-v2` 資料層（ADR-009 T1，issue #935，2026-09-25）**：`20260925170000_add_patient_share_summary_v2.sql` 把 `patient_share_consents`／`patient_share_links` 的 `scope_version` CHECK 擴為 `('daily-summary-v1', 'daily-summary-v2')`（沿用自動產生的約束名），`create_patient_share_link` 接受 v2，並新增只授權 `service_role` 的 `get_patient_share_summary_v2(p_link_id)`。scope 是 link 建立當下固定的屬性：v1 RPC 與 v2 RPC 各自把自己的 scope 寫死在 WHERE，v1 link 打 v2 RPC、v2 link 打 v1 RPC 都得到與 redeem 相同的 `Share link not found`，Function 端再依 session payload 的 `scopeVersion` 分派一次，兩層釘死（ADR-009 決策一）。v2 RPC 回 JSONB 信封而不是 TABLE：`patient_id`／`scope_version` 只供 Function 與 session payload 比對、不進 DTO；其餘只選白名單欄位——近 14 個照護日（台北 04:00 切分）的血壓讀數（`LIMIT 120`＋`total_count`）與 `patient_bp_standards` 的判讀欄位（不含 `prescribed_note`；判讀在 Function 端逐筆依當時標準做）、active 藥單（`active_count`＋`LIMIT 101` 哨兵：超過 100 列由 Function 整份回 503，不出貨半份；不選 `appearance_photo_url`／`instruction_note`／`atc_code`）、30 天內 `health_visit` 與帶 change log 的 `medication_change` 兩型事件（`LIMIT 10`＋`total_count`；不選 `title`／`details`／`visit_institution`／`photo_paths`／`reason`／`actor_email`）、以及 `open_question_count`。撤銷／過期／同意撤回／建立者 `can_share_readonly` 收回的重查條件與現行 v1 相同：建立者以 `created_by_user_id` 認人，只有 `created_by_user_id IS NULL` 的舊連結才退回 `created_by_email`。T1 原版誤抄 2026-09-04 的舊版 v1、只比對 email，帳號改過 email 後 v2 連結會失效而 v1 不會；`20260926075835_align_share_summary_v2_creator_check_with_v1.sql` 補正（issue #979），`tests/unit/shareSummaryV2CreatorCheckMigration.test.ts` 鎖住 redeem、v1、v2 三支的最新定義共用同一段述詞。所有子查詢都以從 link 解析出的 `v_patient_id` 過濾，不接受任何 client 端 id；`supabase/tests/rls-authorization.sql`「share summary v2」段用另一位病人的哨兵資料實測不會混入，`tests/unit/patientShareSummaryV2Migration.test.ts` 鎖 SELECT 清單與授權。v1 的 `get_patient_share_summary` 與 DTO 一字未改；回滾順序見 migration 檔頭。

## 公開與 Demo 邊界

### 原本漏洞（ELI5）

原本是為了讓 Demo 顯示血壓，建立了一扇「公開讀取」的門；但那扇門的條件寫成 `USING (true)`，等於沒有檢查病人身分。任何拿到網站 publishable key 的未登入訪客，都能直接問 Supabase：「請給我 `blood_pressure_records` 的資料。」因為規則說全部都 `true`，同一張表裡不是 Demo 的列也可能被回傳。

這就像店家想讓路人看兩個展示模型，卻把倉庫門貼上「所有人都能進」：Demo 的本機展示本身不是問題，公開「整張健康資料表」才是問題。RLS 的允許規則是加在一起看的；只要有一條規則允許，另一條較嚴格的規則不能把它抵銷。因此 `care_access.patient_id` 雖然保護正式照護資料，仍會被那條全表 `USING (true)` 規則繞過。現在展示資料走 `demoData`／`demoStorage`，資料庫不再需要匿名健康資料入口。

歷史 guest read policy 與 Demo allowlist policy 已由 `20260901020000_revoke_anonymous_health_data_access.sql` 一併移除；它也收回 `PUBLIC`／`anon` 在患者、血壓／體重、服藥、照護時間線、PRN、失智與體液資料表的所有 table privilege，並把未指定角色的既有 policy 收斂到 `authenticated`。因此 publishable key 即使被直接拿去呼叫 REST，也沒有匿名健康資料讀取入口；正式資料仍由 `care_access.patient_id` 的 RLS 授權 authenticated 使用者，不能只依賴前端畫面或 policy 名稱。

## 權限修改檢查表

CI 不只以單元測試搜尋 migration 文字。資料庫相關 PR 會先從空白本機 Supabase 重播 migrations 與 seed，再於同一個 runner 以 `authenticated` PostgreSQL role 與測試 JWT claims 執行 `supabase/tests/rls-authorization.sql`。因為舊核心表的 local migration baseline 沒有 API role 預設 grants，測試只在 disposable transaction 內暫時補上測 policy 所需的最小 table privilege，最後與所有 assertions 一起 rollback，不會把這些 grants 推到 staging／production。測試必須證明核心照護者可讀寫代表媽媽的 patient、view-only 帳號不可寫、未授權帳號查不到資料，而且移除 `care_access` 後權限立即失效；所有測試寫入都包在 transaction 後 rollback。這是為了測到 PostgreSQL 真正套用的 policy 組合，而不是只確認 SQL 檔案包含某段字串。

本機 seed 只代表授權矩陣，不代表 staging／production 真實帳號或健康資料。正式核心帳號的不變量仍須在 staging 用安全測試資料驗證；CI 不得複製 production 紀錄，也不得用 `postgres`／service-role assertion 假裝通過 RLS，因為兩者會繞過 policy。

- 查詢是否每次都帶 `patient_id`，而不是用顯示名稱？
- 表單、快取、圖表、報告與通知切換 patient 後，是否仍可能沿用上一人的生理數值或門檻？
- INSERT 是否驗證病人可寫入範圍與實際操作人？
- UPDATE／DELETE 是否只允許正確 role，且不會藉由任意 email 指定他人？
- 新的病人級表是否掛了 `forbid_patient_id_change`？只靠 policy 擋不住「對兩位病人都有權的人把列改綁到另一位」；漏掛時 `rls-authorization.sql` 開頭的 #976 不變量會讓 replay 失敗。
- RPC 是否使用 `auth.uid()`／JWT，而不是信任 client 傳入的 user id？
- 新 profile 是否先建立再寫 access／plan，避免外鍵或 seed 順序錯誤？
- migration 是否 reload schema，並在 local／staging 驗證直接 API 與 UI 兩條路徑？
- 是否意外恢復匿名讀取健康資料？
- 動到 `care_access`／`household_members`／`patients`／判讀設定表（AUDIT-2 之後含 Tier B 健康表）的寫入路徑時：系統清理是否設 `app.audit_bypass`？在使用者 session 內做的系統決定是否設 `app.audit_actor_kind = 'system'` 並在寫入後還原？新的病人級表是否掛了 `log_record_change()`，而不是另開一張記 email 的 bespoke log？

若文件與程式碼或 migration 不一致，先修正可驗證的現行契約並補 ADR；不要盲目恢復舊 policy。
